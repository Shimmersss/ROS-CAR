### 4.2 感知帧率（已定位；部分改动和测量工具已备，待板上实测）

2026-10-13 无车准备（均为默认关闭或只读，未上板）：
- `scripts/measure_c_rates.py`：替代板上临时 `light_rates.py` 的只读探针，只订阅驱动彩色/深度、校正后 CameraInfo 等小话题，加 Pose 的 `/perception/performance`、目标测量龄和 `/proc` 进程 CPU，输出 JSON，不解码图像。
- `GEMINI_INPROCESS_REGISTRATION=true`：配准并入 Pose 进程（tracker 直接订阅原生 RGB-D，在工作线程里校正/对齐，并自行发布 `camera_info_rect`），省掉每帧约 2 MB 的跨进程发布/反序列化和独立同步。默认 false；与 `REID_ENABLED=true` 互斥（ReID 需要校正彩色话题）。注意这会把约 42 ms 的对齐移进推理同一工作线程、失去原来的跨进程流水并行，**是否更快必须用上面的探针在板上对比**，结果不明前不要设为默认。合成输入下与独立节点的目标位置、校正图像和 CameraInfo 一致。

现状：整栈下 Pose 实际输入只有 6–7 帧/秒，推理本身每帧 37–46 ms，measurement_age 中位 213 ms、最大 442 ms（guard 超时 0.5 s）。已知数据：

- 驱动彩色只有约 14–16.7 Hz（请求 30 Hz，MJPEG）；深度 30 Hz。原因未查（曝光/USB/驱动解码）。
- 深度对齐节点单独约 42 ms/帧，整栈满载时被挤到约 7–8 Hz。
- Pose 节点里 torch CPU 线程空转；`OMP_NUM_THREADS=1` 只让输入从 4–5 升到 6–7 帧/秒（仅启动环境变量，未写进脚本）。
- Python 节点间传 640×480 float32 对齐深度（1.2 MB/帧）。

建议顺序：先用只订阅 `camera_info` 类小话题的探针（`artifacts/light_rates.py`，交接时正要运行）量各段速率和进程 CPU，不要用解码整图的 Python 探针（它本身会抢 CPU）；再试对齐深度改发 16UC1（毫米）、把 `OMP_NUM_THREADS=1` 或 `torch.set_num_threads(1)` 固化、查驱动彩色帧率；必要时把对齐并入 Pose 进程或改 C++。
