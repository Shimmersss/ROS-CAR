# 云端拍照任务 HTTP v0 接口协议

更新日期：2026-10-15；对应拍照推理闭环分支。本文给云端开发者说明小车如何取任务、上传 JPEG 和回传执行状态。ROS 程序的调用方法见[ROS 接口使用手册](ROS接口使用文档.md)第 3 节。

## 1. 先理解两种任务来源

| 来源 | 发起路径 | 云端收到什么 |
|---|---|---|
| 云端下发 | 云端提供 command → 小车 bridge 取到 → 执行器拍照 | ack、阶段 events、JPEG 上传和心跳 |
| ROS 自行发起 | ROS 服务或 Action → 同一个执行器 | JPEG 上传；没有本次 command/ack/events，既有 bridge 心跳仍可反映 busy |

支持 `face / tongue / helmet / pcb` 四类任务。默认 `pipeline_mode=upload` 仍只播报、采集和上传；显式 `infer` 把选中图片交给 5060 独立网关，返回结构化结果和标注图。小车执行器不加载推理模型。上传回执不能代替诊断或检测结果。`tongue` 拍照与语音 `tongue_mode` 的舌苔分析合同独立。

**ROS 上传待正式云端确认：**服务器须允许未经自己下发的任务 ID 上传，并接受 `X-Task-Source: ros_api`。如果服务器只接受自己下发过的 ID，ROS 调用可能得到 `upload_http_404`。本机 mock 默认支持这一点，不能据此认定正式服务已支持。

## 2. 地址、鉴权与数据规则

| 项目 | 规则 |
|---|---|
| 业务根地址 | `CAPTURE_CLOUD_URL`，支持 http/https；正式地址、TLS 和凭据由云端团队确认 |
| 本机 mock 默认 | `http://127.0.0.1:8090`，只供本机联调 |
| 机器人 ID | `CAPTURE_ROBOT_ID`，默认 `roscar-01` |
| 鉴权 | 有 token 时发送 `Authorization: Bearer <token>`；来自 `CAPTURE_CLOUD_TOKEN` 或当前用户拥有的 0600 私有文件 |
| ID 格式 | command_id/task_id/capture_id/upload_id 等匹配 `[A-Za-z0-9_-]{1,64}` |
| JSON | UTF-8 对象，最多 2 MiB；拒绝重复键和 NaN/Infinity |
| 图片 | 原始 JPEG 字节，最多 12 MiB，不是 Base64 JSON |

根地址可以带路径前缀。例如 `https://example.com/roscar/` 规范为 `https://example.com/roscar`，本文 `/v1/...` 路径会接在 `/roscar` 后。前缀段仅接受 `[A-Za-z0-9._~-]+`，拒绝空段、`.`、`..` 和百分号编码；根地址禁止账号、查询和 fragment。

客户端直连，不读取系统代理，也不跟随 HTTP 重定向。凭据不写项目文件、日志或 URL。文档下载用的静态服务器地址不是默认业务根地址。

## 3. 五个 HTTP 端点

下表的方法方向全部为**小车请求云端**。

| 方法与相对路径 | 小车发送 | 云端应返回 |
|---|---|---|
| GET `/v1/robots/{robot_id}/commands/next?wait=1` | 等待时间 wait，整数 0–20 秒 | 200 + 一条指令 JSON；无指令时 204 |
| POST `/v1/robots/{robot_id}/commands/{command_id}/ack` | 是否接受及原因 | 2xx，可为空响应 |
| POST `/v1/robots/{robot_id}/tasks/{task_id}/events` | 阶段、detail、seq；结束可含 result | 2xx，可为空响应；同一 seq 重传应幂等 |
| POST `/v1/tasks/{task_id}/images` | JPEG 与元数据头 | 200 + 合法 received 回执；幂等冲突可用下文的 409 合同 |
| POST `/v1/robots/{robot_id}/heartbeat` | 状态和资源健康信息 | 2xx，可为空响应 |

### 3.1 轮询行为

小车 `poll_wait_sec` 默认 1，launch 同名参数或 `CAPTURE_POLL_WAIT_SEC` 可设为 0–20 的整数；非法值启动报错。默认空闲约 1 请求/秒，有待发事件时请求 wait=0；HTTP 总预算和 socket 预算为实际 wait+2 秒。

云端一有指令就应立即返回，不必等满 wait。bridge 只有一个 HTTP 工作线程，调大 wait 会使待发事件、心跳和取消处理额外延迟最多 wait 秒。心跳目标间隔 10 秒，不保证长轮询下严格每 10 秒送达。

## 4. 云端如何下发拍照与取消

### 4.1 拍照指令

GET commands/next 的 200 响应示例：

```json
{
  "command_id": "c-001",
  "type": "capture",
  "task_id": "t-001",
  "task_type": "pcb",
  "params": {"prepare_sec": 3},
  "ttl_sec": 60
}
```

| 字段 | 规则 |
|---|---|
| `command_id` | 必填；每条指令唯一，供 ack 和 10 分钟去重 |
| `type` | 必填，本次为 capture |
| `task_id` | 必填；每次业务拍照使用新 ID，取消时按它匹配 |
| `task_type` | 必填；face / tongue / helmet / pcb，具体目录由 tasks.yaml 定义 |
| `params` | 可省略，默认空对象；只允许 announce / prepare_sec |
| `ttl_sec` | 可省略或 0，采用默认 60 秒；其他值大于 0、最多 600 秒 |

自定义 `announce` 须非空、最多 300 字符，经过 Unicode 规范化、忽略标点空白后不得含 `RESERVED_STOP`（完整列表见 `capture_task/catalog.py`）。自定义 `prepare_sec` 为 0–30 秒。不能通过 params 更改质检、上传方式或安全配置；多余字段会被拒绝。

云端 TTL 从 bridge 收到指令时开始；转交执行器时会扣除已耗时间。忙时直接 ack busy，不排队。

### 4.2 取消指令

```json
{"command_id":"c-002","type":"cancel","task_id":"t-001"}
```

只取消 bridge 自己持有的匹配任务，不取消 ROS 服务或其他直接 Action 发起的任务。取消不能撤回云端已收到的图片。

`speak` 在协议校验中保留，但当前 bridge 返回 `unsupported`；不要把它当作已经支持的云端播报功能。需要文字播报使用[ROS 接口](文字播报ROS接口.md)。

### 4.3 ack

```json
{"accepted":true,"reason":"accepted"}
```

`accepted=true` 表示任务已被接受，不表示拍照完成。失败 ack 为 `accepted=false`，reason 可能为 busy / invalid / expired / voice_mode_active / rejected / not_active / unsupported / unavailable 等；取消成功的 reason 为 `cancel_requested`。

无法安全识别 command_id 的无效指令不一定有 ack。command_id 在进程内保留完整 10 分钟去重；重复指令重发原 ack，不再次执行，进程重启不保证保留去重状态。

## 5. JPEG 上传与回执

Content-Type 为 `image/jpeg`，body 为 JPEG 原始字节。

| 请求头 | 含义 |
|---|---|
| `X-Robot-Id` | 机器人 ID |
| `X-Task-Type` | face / tongue / helmet / pcb |
| `X-Capture-Id` | 本张图片的采集 ID |
| `X-Frame-Index` | 本次选中上传图片的索引，从 0 起 |
| `X-Capture-Time` | 图像帧时间转换的 UTC ISO8601 时间 |
| `X-Camera-Profile` | 相机配置标识，默认 raw_rgb_v1 |
| `X-Image-Sha256` | JPEG 的 SHA256 |
| `X-Quality` | JSON：brightness / sharpness / rb_ratio / width / height 数值 |
| `X-Task-Source` | 当前执行器发送 cloud / ros_api / local_test；云端应兼容旧客户端不带此头 |

当前默认质量策略为 `warn`：宽度、亮度、清晰度或 R/B 比不足时仍上传原始指标，不放大图片、不伪造达标。目录设为 `fail` 才在质检失败时中止上传。完整任务默认值见[ROS 手册](ROS接口使用文档.md)。

正常回执（HTTP 200）：

```json
{"status":"received","task_id":"t-001","capture_id":"cap-001","upload_id":"u-001"}
```

task_id 和 capture_id 必须原样回显，upload_id 必须符合 ID 格式。小车只保留校验后的字段，不接受任意云端文字用于播报。客户端校验后的回执会附带本地计算的 sha256。

同 capture_id 重传可返回 HTTP 409；只有下列回执中 sha256 与本次图像完全一致，且其他字段合法，才视为幂等成功：

```json
{"status":"received","task_id":"t-001","capture_id":"cap-001","upload_id":"u-001","sha256":"<本次JPEG的SHA256>"}
```

一般 4xx 不重试；5xx 和网络错误最多尝试三次，间隔 1、2 秒，并受任务总时限约束。取消会关闭当前上传连接，但服务端可能已经保存数据。

## 6. 阶段事件与心跳

阶段事件：

```json
{"phase":"CAPTURE","detail":"","seq":1}
```

执行流程通常为 CHECK → robot 下 HOLD → ANNOUNCE → PREPARE → CAPTURE → QUALITY → UPLOAD → DONE_ANNOUNCE → UPLOADED。结束事件还可带 result，其中 `upload_json` 在 HTTP event 中是已解析的回执数组；ROS Action/Service 中同名字段是 JSON 字符串。失败或取消结果为 FAILED / CANCELLED。

seq 按 task_id 在当前进程内递增；云端对重传同一事件应幂等。重启后不保证事件序列和重放，云端须按任务 ID、图片 ID 与回执对账；不要把事件通道当作持久消息队列。

心跳示例：

```json
{"state":"idle","task_id":"","camera_ok":true,"tts_ok":true,"version":"0.1.0"}
```

state 为 idle / busy / unknown，反映执行器资源状态，不表示底盘获准运动。执行器状态超过 1.5 秒未更新时，新拍照指令 ack unavailable，心跳置 unknown、camera_ok=false、tts_ok=false；ROS 的 bridge_state 同时标注 executor_stale。

语音舌苔模式 active 时拒绝拍照，执行中也监测互斥。执行模式状态超过 6.5 秒未刷新视为不活跃；解析失败按 active 处理，使用相同期限。时效判断基于本机 monotonic 接收时间。

## 7. 网络和鉴权失败

- 轮询断网按 1、2、4……30 秒退避。
- 401/403 进入 auth_failed，60 秒后重试；执行器上传出现相同错误也会使 bridge 进入该状态。
- bridge 自身不会播报网络故障；已接受任务执行失败，执行器会尽力播报一次安全失败提示。取消、程序关闭、TTS 自身失败等情况下不补播。
- 未送达的 ack/events 使用有界内存队列重试，进程重启不保证重放。

## 8. 本机 mock 联调

参考实现为 `scripts/mock_capture_cloud.py`，不是多机器人生产调度系统。以下 admin 端点只供本机调试，不属于生产 `/v1/` 合同：

```bash
# 终端 A：启动 mock，图像只写入已忽略的 artifacts
python3 scripts/mock_capture_cloud.py serve --store artifacts/capture-mock
# 终端 B：需已有 bridge/执行器；只入队不会凭空开始拍照
python3 scripts/mock_capture_cloud.py send pcb
python3 scripts/mock_capture_cloud.py status
# 将 t-001 换成 send/status 输出中的实际任务 ID
python3 scripts/mock_capture_cloud.py cancel t-001
```

路径前缀联调时，服务端、执行器/bridge 和工具使用相同前缀：

```bash
python3 scripts/mock_capture_cloud.py serve --prefix /roscar
# 执行器/bridge 配置 CAPTURE_CLOUD_URL=http://127.0.0.1:8090/roscar
python3 scripts/mock_capture_cloud.py --url http://127.0.0.1:8090/roscar send helmet
python3 scripts/mock_capture_cloud.py --url http://127.0.0.1:8090/roscar status
```

| serve 参数 | 模拟场景 |
|---|---|
| `--fail-upload 500`、`401`、`409` | 上传错误；409 先保存同 SHA 图像再返回幂等回执 |
| `--slow-upload 10` | 慢上传与任务 TTL |
| `--drop-poll` | 轮询失联 |
| `--reject-unknown-task` | 只允许通过 commands/next 下发过的 task_id；ROS 自行生成 ID 返回 404，默认关闭 |

验证边界、启动安全条件和实机待验收项见[实现与验收](云端拍照任务实现与验收.md)。

## 9. 显式 infer 模式：分析结果与标注图

只有部署时选择 `CAPTURE_PIPELINE_MODE=infer` 并配置 `CAPTURE_INFERENCE_URL` 才使用本节；原 command/ack/cancel 字段不变，不能在任务 params 中切换模式。推理网关认证使用单独的 `CAPTURE_INFERENCE_TOKEN_FILE`（0600），与云端指令方 token 分开。

执行顺序为 CHECK → robot 下 HOLD → ANNOUNCE → PREPARE → CAPTURE → QUALITY → INFER → DONE_ANNOUNCE → ANALYZED/RETAKE。失败、取消仍为 FAILED/CANCELLED。播报使用本地固定短句，不直接播放网关提供的文字。

### 9.1 最终 event

仍 POST `/v1/robots/{robot_id}/tasks/{task_id}/events`，例如：

```json
{
  "phase": "ANALYZED", "detail": "ok", "seq": 12,
  "result": {
    "status": "analyzed", "detail": "ok", "capture_id": "cap-001",
    "upload_json": [],
    "analysis": {
      "status": "ok", "task_type": "pcb", "request_id": "infer-001",
      "task_id": "t-001", "capture_id": "cap-001",
      "model": {"name":"pcb","version":"8.4.174","weights_sha256":"<SHA256>","device":"cuda:0"},
      "image": {"width":640,"height":480},
      "result": {"defects":[],"reject":false,"conf_threshold":0.2,"imgsz":640},
      "summary": {"positive":false,"count":0,"text_key":"pcb_defects"},
      "annotated_image": {"content_type":"image/jpeg","width":640,"height":480,"sha256":"<JPEG SHA256>"},
      "timings_ms": {"queue":0,"decode":1,"inference":20,"annotate":2,"total":23}
    }
  }
}
```

`analysis` 是网关响应去掉图片 base64 后的对象。网关 `ok/uncertain` 映射为任务 `analyzed`；`retake` 映射 `retake`，没有标注图；`model_unavailable/busy/timeout/invalid_input/error` 映射 `failed`，detail 表明原因。`analyzed` 只表明链路和分析完成，不保证目标确实存在或模型准确。

PCB 结果为六类 defects（原图 xyxy、score、cls、name）及 reject；helmet 为 detections、helmet_count、no_helmet_count、violation；tongue 为冻结 pipeline_id/digest、classification_performed、八标签 score/threshold/decision、positives、quality、roi。面诊目前无模型，明确失败，不伪造成功。完整网关合同见 [网关说明](../services/inference_gateway/README.md)。

### 9.2 分开返回图片

最终 event 获得成功应答后，独立线程 POST `/v1/tasks/{task_id}/result-image`：

| 请求头 | 内容 |
|---|---|
| Content-Type | image/jpeg |
| X-Capture-Id | 与最终 event 一致 |
| X-Image-Sha256 | 本次 body 的 SHA256 |
| X-Image-Kind | annotated；显式返回原图时为 original |

body 是 JPEG 原始字节。回执须完整回显并核对哈希：

```json
{"status":"received","task_id":"t-001","capture_id":"cap-001","sha256":"<本次JPEG SHA256>"}
```

匹配哈希的 409 也视为幂等成功。图片传输最多三次，退避 1、2 秒，单次 2 秒预算；一般 4xx 不重试，429 可重试。失败记录 `IMAGE_RETURN_FAILED`，不会把推理成功改写为模型失败，也不会阻塞后续取指令。云端必须分别确认分析 event 和图片回执，不能收到 ANALYZED 就假定图片已保存。

图片队列至多 16 项、32 MiB（含正在传输的图片），进程重启不保证重放。默认仅返回标注图；只有部署显式 `CAPTURE_RETURN_ORIGINAL_IMAGE=true` 才额外返回原图。原图经内部非持久 ROS 话题传输，不进入结果 JSON，也不默认保存。infer 不再调用旧 `/images`，upload 不调用本节 `/result-image`。

### 9.3 mock 查询结果

```bash
python3 scripts/mock_capture_cloud.py send pcb --ttl 180 --task-id t-001
python3 scripts/mock_capture_cloud.py result t-001
```

查询返回最终 result、图片 SHA256 和保存路径。`--reject-unknown-task` 同时约束最终事件和结果图片，ROS 自行发起的 `/inspect/*` 直接把结果交给调用方，不生成云端 ack/events/result-image。静态文档服务器仍不是业务服务。
