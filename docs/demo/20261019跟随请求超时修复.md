# 2026-10-19 跟随请求超时诊断与修复

本轮针对刚授权跟随后出现 `request_timeout` 的故障；不调整 ReID 阈值、200 ms 请求超时、目标宽限或非目标故障锁存。

## 实录证据

- `data/demo-trials/20261019-182851-continuity-v2-ready`：首次 request_timeout 在 ROS bag 时间 `1792405795866339425 ns`。其前后请求发送约 50 ms 一次；最近一条发送在故障前约 41.8 ms，并在故障前约 40.0 ms 已被 bag 收到。guard 状态输出前一条却距故障约 267.7 ms。说明该次故障并非跟随器停发，而是 guard 接收/检查调度存在停顿。录像不能单独证明是哪一个 ROS/C 调用阻塞，不能断言一定是某次 count_publishers 调用。
- `20261019-183015-fresh-central`：另有一次实际请求发送时间戳间隔约 313.0 ms。它与上述触发故障时刻不同，说明发送侧也需要调度隔离。
- 当时 guard 在 CPU5，follower 在 CPU0–3，与视觉/其他任务共用；Pose 在 CPU2–3。系统六核负载约 6.7，已用交换约 1.1 GiB；仅凭这些数值不能证明内存或某一进程是唯一原因。

## 采用的改动

1. guard 使用两个执行线程，只把 FOLLOW/EXTERNAL 请求接收放入独立互斥回调组。图查询等检查期间仍可接收新请求。授权、模式切换、STOP、ESTOP、跌倒处理、TaskHold 和最终速度发布仍在同一个默认互斥组内，禁止并发改变运动状态。
2. 请求、接收时刻和模式切换清理受同一把短锁保护。检查在图查询后取得消息/时刻快照；从时间戳、frame、速度检查到输出都使用该快照，不用半途到达的新消息替换已验证消息。
3. 授权同时要求已验证快照和锁内最新请求均为零，并在锁内提交授权，保留“不能从缓存非零速度起步”。
4. 既有可选 CPU 布局把 person_follower 与 guard 放在 CPU5，离开 Pose 的 CPU2–3；脚本仍只处理指定启动器的后代进程，不更改外部任务。默认未启用 CPU 布局的通用入口不受此规则影响。

这些改动不使非目标故障自动恢复，也不关闭发布者唯一性、frame、测量龄期、急停或底盘看门狗。检查本身若真的卡住，最终控制的延迟仍需继续观察；两个执行线程不构成硬实时保证。

## 验证

新增 `tests/test_guard_request_scheduling_runtime.py`，限定 localhost ROS_DOMAIN_ID=222，真实 guard 节点、合成输入，所有最终速度为零：

- 单线程执行器下人为延迟一次检查 270 ms，稳定复现 request_timeout。
- 双线程及独立请求回调下，同样延迟不误报请求超时。
- 真正停发请求，仍按原 200 ms 期限故障锁存，恢复发送不能自动解除。
- 已验证请求为非零时，即使最新消息是零，也不能授权。

测试已加入 demo 容器及流程回归入口。Jetson 原生 motion_guard 编译与新回归通过；既有目标宽限/时钟回拨/急停/非目标锁存及 TaskHold 回归通过。Humble 容器中跌倒暂停、失效告警、主人冻结、手动恢复和 ESTOP 联动回归通过。车上有负载时，该跌倒回归先后在两个恢复时刻断言失败，未跳过或修改其断言；不能把隔离容器结果当成负载下实车跌倒恢复验收。

19 项 guard/CPU 布局纯 Python 测试及完整本机 CI 退出 0。沿用现有 Humble 镜像、Jetson 环境，无新增模型或环境下载；临时容器自动删除。
