## 1. 接底盘时自动打开跟随控制器【必须】

**位置**：`scripts/start_project.sh:76`

**现象**：`WITH_CAPTURE_TASKS=true` 且 `WITH_CHASSIS=true` 时，脚本会悄悄执行 `WITH_FOLLOWER=true`。这样启动的 `motion_guard follow.launch.py` 除了 guard，还带人体跟随控制器 person_follower（`target_distance_m:=1.0`）。用户只是想用拍照，却被额外打开了跟随功能。现在默认 `MOTION_ENABLED=false`，所以不会动；但如果用户同时设了 `MOTION_ENABLED=true`，一旦授权，小车就会开始跟人。

**修改要求**：

- 删掉这条自动赋值，改成与舌苔模式一致的显式校验：`WITH_CHASSIS=true` 而 `WITH_FOLLOWER` 不是 `true` 时，直接报错退出，退出码 2。提示语示例：`接底盘的云端拍照需要唯一 guard，请显式设置 WITH_FOLLOWER=true（会同时启动跟随器，运动仍受 MOTION_ENABLED 与授权约束）。`
- `CAPTURE_SAFETY_PROFILE=robot` 的判定保留不变。
- **不要**为了"只启动 guard、不启动 follower"在 start_project 里新增第二个 guard 入口，那样可能出现两个 `/cmd_vel` 所有者。仅 guard 的方案如果要做，单独提出，经用户确认后再改。
- 同步修改：`start_project.sh --help` 文案、`AGENTS.md`（"接底盘强制 robot + 唯一 guard"一句）、实现与验收文档 §4。

**验收**：

- 在现有入口门控测试中补充以下用例，只验证参数校验，不启动硬件：
  - `WITH_CAPTURE_TASKS=true WITH_CHASSIS=true`，未设 `WITH_FOLLOWER`：退出码 2，输出上述提示；
  - `WITH_CAPTURE_TASKS=true WITH_CHASSIS=true WITH_FOLLOWER=true`：通过门控，并使用 robot 配置；
  - 无底盘的 bench 规则保持不变：`WITH_FOLLOWER=true` 或 `MOTION_ENABLED=true` 时拒绝。
- 用 `git grep -n 'WITH_FOLLOWER=true$' scripts/` 确认不再有自动赋值。

## 2. 大部分失败情况不播报失败提示【必须】

**位置**：`ros2_ws/src/capture_task/capture_task/executor_node.py`，第 333 行（`upload()` 异常分支执行 `self.job.cancel.set()`）和第 365–369 行（失败分支调用 `self.speak(fail_announce)`）。

**现象**：`speak()` 一开始会调用 `check()`。而失败时任务往往已被标记为取消（上传异常时自己置了 `job.cancel`），或者已经超时、已有 `safety_error`、语音模式处于 active，`check()` 会再次抛异常，异常又被 `except Exception: pass` 吞掉。结果是：上传失败（例如云端连不上）、任务超时、质检不通过、停车保持失败、静止校验失败时，现场的人听完"即将拍照"后再也听不到任何声音。只有相机缺失这类在 CHECK 阶段就失败的情况会播报。

**修改要求**：

- 区分"内部中止"和"外部取消"。上传失败时不要再设置 `job.cancel`，改用只给上传使用的 `upload_cancel` 事件，也可以直接调用 `cloud.cancel()`。这样 `job.cancel` 只表示两种情况：云端或 ROS 发来的取消，以及节点关闭。
- 新增 `speak_failure()`，**不要调用 `check()`**，规则如下：
  - 以下情况不播报：节点正在关闭（`closing`）、`rclpy` 已不可用、外部取消（`job.cancel`，或 `goal.is_cancel_requested`）、本次失败原因就是 TTS 本身（`tts_unavailable`、`tts_rejected`、`tts_not_completed`）。
  - 其余失败一律播报 `fail_announce`，包括 `task_timeout`、`fresh_frame_timeout`、`quality_failed:*`、`upload_http_*`、`network_*`、`deadline_exceeded`、`invalid_receipt`、`hold_*`、`stationary_*`、`odom_*`、`emergency_unhealthy`、`camera_publisher_count`、`bench_velocity_publisher`、`voice_mode_active`。
  - 使用独立的时限：`min(speech_timeout_sec, 15 秒)`，不受 `job.deadline` 限制。等待期间如果节点关闭或发生外部取消，就取消这次播报的 goal。
  - 迟到的接受仍要处理：做法同现有 `late` 回调，任务结束后才被接受的 goal 要主动取消。
  - 只能播报目录中配置的安全文本，绝不能把错误字符串送去 TTS。
- 失败播报本身失败时，不得改变任务的 `status` 和 `detail`。可以在 events 里额外记一条 `fail_announce_skipped:<原因>`。
- 播报失败提示期间仍持有停车保持（robot 配置），播报结束后再释放。现有 finally 的执行顺序请保持"先播报、后释放"。

**验收**：在 `tests/test_capture_task_runtime.py` 中增加断言，判断假 TTS 是否收到 `fail_announce` 原文：

| 场景 | 期望 |
|---|---|
| mock `--fail-upload 500`（重试 3 次后失败） | 播报 |
| mock `--fail-upload 401` | 播报，并且 bridge 进入 auth_failed |
| `ttl_sec` 很短、在 PREPARE 阶段超时 | 播报 |
| quality_policy=fail 且图像不达标 | 播报 |
| cloud `cancel` 指令或 ROS cancel | **不**播报 |
| SIGTERM | **不**播报 |
| robot 场景：静止校验失败（假 odom 给速度） | 播报，且播报完成后租约才释放 |

另外在 `test_flow.py` 中用注入接口补充：失败播报抛异常时，最终 result 的 `status`/`detail` 不变。

## 3. 本机联调脚本依赖 `rg`【必须】

**位置**：`scripts/run_capture_tasks_local.sh:21` 和 `scripts/run_capture_tasks_local.sh:28`

**现象**：普通终端和 Jetson 上没有 ripgrep，`rg` 会返回退出码 127，`if`/`elif` 判定为假，于是两道保护被静默跳过：

- 检查隔离域里是否已经有 `/voice/speak`，防止重复启动第二个播报所有者；
- 检查系统 usb_cam 是否存在时间戳单位问题，有问题就拒绝启动。

验收方用 `bash -c` 实测：命令返回 127，脚本走了"未检测到"的分支。agent 自己的环境自带 `rg`，所以没有发现。

**修改要求**：

- 两处都改为 `grep`：
  - 第 21 行：`grep -Fq 'epoch_time.tv_usec / 1000.0' /opt/ros/humble/include/usb_cam/utils.hpp`
  - 第 28 行：`ros2 action list 2>/dev/null | grep -Fxq /voice/speak`
- 第 28 行的 `ros2 action list` 本身失败时（例如 ROS 环境异常），要明确报错退出，不要当作"不存在"。
- 用 `git grep -nwE 'rg' -- scripts tests ros2_ws/src/capture_task` 检查本分支新增文件里是否还有其他 `rg` 依赖，有就一并替换。

**验收**：

- 在去掉 rg 的 PATH 下运行两个检查分支，例如 `env PATH=/usr/bin:/bin bash scripts/run_capture_tasks_local.sh ...`：
  - 已存在 `/voice/speak` 时拒绝启动（可以先用 fake_tts 单独占住 190 域）；
  - 头文件含错误写法、且没有修正 overlay 时拒绝启动。可以用临时副本配合可注入的头文件路径变量来测，**不要修改 `/opt/ros`**。
- `bash -n` 和 shellcheck（如果已安装）通过。

## 4. 帧新鲜度判断比舌苔模式更严

**位置**：`ros2_ws/src/capture_task/capture_task/frames.py:92`

**现象**：判断条件是 `0 <= ros_now()-frame.ros_stamp <= max_age`，只要时间戳比本机时钟稍早一点（负的 ROS 帧龄）就拒绝。`tongue_mode/node.py` 对同一件事允许 `-0.05` 秒。车上的 astra/Gemini 驱动如果按设备时钟换算时间戳，可能出现几十毫秒的超前，导致一直报 `fresh_frame_timeout`。

**修改要求**：

- 允许最多 0.05 秒的未来时间戳：`-MAX_FUTURE_STAMP <= ros_age <= max_age`，其中 `MAX_FUTURE_STAMP = 0.05`。做成模块常量即可，不要加入 tasks.yaml，免得扩大目录 schema。
- 接收龄（monotonic）仍要求 `>= 0`。
- `frame.ros_stamp > ros_after` 的条件保留。
- 在实现文档里写明这个容差及理由（与舌苔一致）。

**验收**：`test_flow.py` 或新增的 `test_frames.py` 覆盖以下情况：

| 时间戳相对本机时钟 | 期望 |
|---|---|
| 超前 0.03 秒 | 接受 |
| 超前 0.08 秒 | 拒绝 |
| 落后 0.4 秒 | 接受 |
| 落后 0.6 秒 | 拒绝 |

并补一条：采集窗口开始之前的帧仍被拒绝。

## 5. 取指令实际上每秒轮询一次，与协议描述不一致

**位置**：`ros2_ws/src/capture_task/capture_task/bridge_node.py:239`（`wait=0 if self.outbox else 1`）。协议文档 `docs/云端拍照任务接口协议.md:11` 写的是"最长等 20 秒"。

**现象**：因为单个 HTTP 线程既要轮询又要发送事件和心跳，代码把 wait 固定成 1 秒，每台车大约每秒发一次请求。功能本身没问题，但云端团队按文档会设计成 20 秒的长轮询，与实际流量不符。

**修改要求**（本轮不重构为双线程）：

- 新增 bridge 参数 `poll_wait_sec`：默认 1，合法范围 0–20 的整数，非法值启动即报错。outbox 不为空时仍使用 0。
- launch 和 `start_project.sh` 透传 `CAPTURE_POLL_WAIT_SEC`，可选。
- 协议文档改为：服务端必须支持 `wait=0..20`；小车默认 `wait=1`，约 1 次/秒，有待发事件时 `wait=0`；心跳 10 秒一次。说明调大 wait 的代价：事件、取消、心跳会被推迟最多 wait 秒。实现文档同步修改。
- 请求超时要大于 wait：当前 `request(..., timeout=2.)` 搭配 wait=1 没问题；参数调大后，GET 的超时要设为 `poll_wait_sec + 2`。

**验收**：

- 单测覆盖：参数校验；GET 的 URL 中的 wait 值；有待发事件时 wait=0；超时时间随参数变化。
- 运行时测试用 `poll_wait_sec=5` 跑一次端到端，确认 cancel 在 5 秒内生效（mock 有新指令时立即返回）。

## 6. 状态消息不会过期

**位置**：

- 执行器 `executor_node.py:92-96`（`on_mode`）及第 135、188 行（使用 `self.mode`）；
- bridge `bridge_node.py:55-65`（`on_executor_state`、`on_mode`）及第 133–136、234–236 行。

**现象**：

- 执行器：`/execution_mode/state` 最后一条消息如果是 `active=true`，而 manager 随后崩溃不再发布，云端拍照会一直被拒，直到重启。`mode_at` 有记录但从未使用。
- bridge：`/capture_task/state` 最后一条如果是 `active=true`，而执行器随后崩溃，bridge 会一直回 `busy`，心跳也一直报告 busy 以及过时的 camera_ok/tts_ok。

**修改要求**：

- 执行器：`/execution_mode/state` 超过 **6.5 秒**未更新时，视为不活跃。舌苔模式在 manager 心跳中断 6 秒后会自行退出，所以这个阈值不会和正在运行的舌苔模式重叠；在源码注释中写明这个依据。从未收到过消息的情况保持现状（视为不活跃）。解析失败仍视为 active，即 fail-safe，但同样受过期规则约束。
- bridge 的 `/execution_mode/state` 使用同样的规则。
- bridge 的 `/capture_task/state`（执行器每 0.25 秒发布一次）超过 **1.5 秒**未更新时，视为执行器不可用：
  - 新的拍照指令回 ack `unavailable`，而不是 `busy`；
  - 心跳中 `state='unknown'`、`camera_ok=false`、`tts_ok=false`；
  - `/capture_task/bridge_state` 增加 `executor_stale: true` 字段。
- 所有时间判断都用 `time.monotonic()`。

**验收**：

- 运行时测试：发布一次 `active=true` 后停止发布，6.5 秒内拒绝，之后接受；mock 下发指令时，执行器节点已停止但 bridge 仍在运行，期望 ack `unavailable`，心跳为 unknown。
- 单测覆盖过期判断函数的边界值。

## 7. 云端地址不能带路径前缀

**位置**：`ros2_ws/src/capture_task/capture_task/cloud_client.py:48`

**现象**：只接受 `path in ('', '/')`。云端如果部署在反向代理的子路径下（例如 `https://host/roscar`），就无法配置。

**修改要求**：

- 允许路径前缀，例如 `https://host/roscar` 或 `https://host/roscar/`：
  - 去掉末尾的 `/` 后保存为 `self.prefix`；
  - 每段只允许 `[A-Za-z0-9._~-]`，拒绝空段（`//`）、`.`、`..` 和百分号编码；
  - 仍然拒绝凭据、query 和 fragment。
- `request()` 实际请求 `self.prefix + path`。`path` 仍须以 `/v1/` 开头，这是内部断言。
- 执行器和 bridge 共用同一个 CloudClient，二者都要生效。
- mock 增加可选的 `serve --prefix /roscar`。协议文档和实现文档注明可以使用前缀。

**验收**：

- 单测：合法前缀拼接正确；`//`、`..`、`%2e`、query、凭据都被拒绝；无前缀时行为不变。
- 运行时测试：mock 使用 `--prefix /roscar`，跑一次完整的上传端到端，SHA 一致。
