## 0. 需求变化与本轮目标

**原流程**：指令 → 小车播报 → 拍照 → **上传 JPEG 给云端** → 回执。推理与小车无关。

**新流程**：

```
指令方（云端 HTTP 或 ROS 调用者）
   │ 下发 face / tongue / helmet / pcb
   ▼
小车：播报 → 准备 → 采集新鲜帧 → 质检 → 把图片发给【该任务的推理接口】
   │                                      │
   │                       返回：结构化结果 + 标注后的图片
   ▼
小车把"结构化结果 + 标注图片"返回给发出指令的那一方（可选：播报一句结果摘要）
```

本轮目标：

1. 在 **5060 笔记本的 WSL**（MeatShell 会话 `5060wsl`，RTX 5060 Laptop 8 GB）上，部署 `E:\models` 中的三个模型（PCB、安全帽、舌象），并在前面加一个**统一推理网关**。
2. 改造车端 `capture_task`，新增"推理模式"：小车把图片发给网关，拿回结果和标注图，经 ROS 服务或云端协议返回给指令方。
3. 在不动小车开机服务的前提下，把闭环逐级跑通：先在 5060 本机，再到本地开发机（Humble + Gemini），最后（需用户另行授权）到小车。

**face 目前没有模型**（`E:\models\face` 为空）。网关对 face 返回 `model_unavailable`，车端如实报失败。以后补上模型时只改网关配置。

## 2. 总体架构

```
┌──────────────────────────── 5060 WSL ────────────────────────────┐
│  inference_gateway  :8200 (0.0.0.0, Bearer)                       │
│    ├─ pcb    : ultralytics 进程内加载 best.pt (cuda:0)              │
│    ├─ helmet : ultralytics 进程内加载 helmet-yolov8l.pt (cuda:0)    │
│    ├─ tongue : HTTP 代理 → 127.0.0.1:8096 舌象原包服务（独立 venv）   │
│    └─ face   : model_unavailable                                   │
│    统一：结果 JSON + 标注 JPEG                                       │
│  mock 云端（指令方）:8090 —— 现有 MockCloud + 本轮新增的结果接收接口      │
└───────────────────────────────────────────────────────────────────┘
          ▲ 推理请求/响应                          ▲ 指令 / 事件 / 结果
          │                                       │
┌─────────┴────────── 车端（或本地开发机）───────────┴───────────────┐
│ capture_task executor：pipeline_mode=infer                        │
│   播报 → 准备 → 采集 → 质检 → INFER（发图给网关）→ 播报摘要           │
│ bridge：云端指令 → action；结束时回传 结果 JSON + 标注图               │
│ api_node：/inspect/<task>（新）同步返回 结果 JSON + 标注图             │
└───────────────────────────────────────────────────────────────────┘
```

设计决定：

1. **车端只对接一个网关，网关后面再分发到各模型。** 小车只需配置一个地址，契约统一，以后加 face 或换模型都不用改车端。舌象原包的 HTTP 服务保持原样，只在它前面做代理。
2. **标注图由网关生成。** 网关手里有模型输出，最适合画框。舌象服务不返回图片，网关根据其 roi 坐标和状态画一张简单标注图。
3. **保留原"上传模式"。** 执行器新增参数 `pipeline_mode: upload | infer`，**默认仍为 `upload`**，现有测试与行为不变。本轮联调在启动时显式设为 `infer`，等用户确认后再决定是否改默认值。
4. **两条回传路径都支持。** 指令方是 ROS 调用者时，走新的 `/inspect/<task>` 服务同步返回；指令方是云端时，由 bridge 把结果 JSON 和标注图回传给云端。
5. **网关只有一个 GPU worker，串行推理**，排队上限是有限的，排满时返回 `busy`。

## 3. 接口契约（先固定，便于并行开发）

### 3.1 推理网关 HTTP（5060 上，新增）

```
POST /v1/infer/{task_type}            task_type ∈ face|tongue|helmet|pcb
请求体：原始 JPEG/PNG 字节（≤12 MiB），Content-Type: image/jpeg
请求头：Authorization: Bearer <token>（网关配置了 token 时必填）
       X-Request-Id, X-Task-Id, X-Capture-Id, X-Robot-Id, X-Capture-Time（与现有上传头一致）
GET  /health/live
GET  /health/ready                    各后端 ready 状态、device、显存
GET  /v1/models                       各任务的模型名、版本、权重 SHA256、类别、阈值
```

成功时返回 HTTP 200，JSON 不超过 8 MiB：

```json
{
  "status": "ok",                     // ok | uncertain | retake | model_unavailable | invalid_input | busy | timeout | error
  "task_type": "pcb",
  "request_id": "...", "task_id": "...", "capture_id": "...",   // 原样回显
  "model": {"name": "pcb_yolo26m_pku640", "version": "v1", "weights_sha256": "9923d4…", "device": "cuda:0"},
  "image": {"width": 640, "height": 480},
  "result": { ... 各任务专属，见下 ... },
  "summary": {"positive": true, "count": 2, "text_key": "pcb_defects"},   // 供车端生成播报，不含自由文本
  "annotated_image": {"content_type": "image/jpeg", "width": 640, "height": 480,
                      "sha256": "...", "data_b64": "..."},                 // retake/错误时可以为 null
  "timings_ms": {"queue": 0.0, "decode": 0.0, "inference": 0.0, "annotate": 0.0, "total": 0.0}
}
```

各任务的 `result` 字段：

- **pcb**：
  ```json
  {"defects": [{"cls": 0, "name": "missing_hole", "score": 0.83, "xyxy": [x1, y1, x2, y2]}],
   "reject": true, "conf_threshold": 0.20, "imgsz": 640}
  ```
  `reject` = 存在任一缺陷。
- **helmet**：
  ```json
  {"detections": [{"cls": 1, "name": "no_helmet", "score": 0.77, "xyxy": [...]}],
   "helmet_count": 2, "no_helmet_count": 1, "violation": true,
   "conf_threshold": 0.45, "iou": 0.45, "imgsz": 640}
  ```
  类名取自 `model.names`。
- **tongue**：
  ```json
  {"pipeline_id": "...", "pipeline_digest": "...", "classification_performed": true,
   "labels": {...8 项原样...}, "positives": [...], "quality": {...}, "roi": {...}}
  ```
  网关要校验原服务返回的 `pipeline_id` 和 `digest` 与 `expected_pipeline.json` 一致，且标签集合正好是那 8 项，不一致返回 `error`。原服务的 `retake/busy/timeout/invalid_input/error` 原样映射到 `status`；`ok/uncertain` 原样保留。

约束：

- 坐标一律是**原图像素坐标**。标注图默认与原图同尺寸，最长边超过 1280 时等比缩小，JPEG 质量 90。
- 网关**不得**返回或记录 token。图片默认**不落盘**，`--save-dir` 只用于调试，且必须指向被 Git 忽略的目录。
- `status` 不是 ok/uncertain 时，HTTP 也返回 200，靠 `status` 区分。只有协议错误（路径不存在、未鉴权、请求体过大）才使用 4xx。

### 3.2 车端 ROS 接口（增量）

1. **`CaptureTask.action` 的 Result 末尾追加两个字段**，原有字段保持不变：
   ```
   string result_json                        # infer 模式下为网关响应去掉 annotated_image.data_b64 后的 JSON；upload 模式为空
   sensor_msgs/CompressedImage annotated_image   # infer 模式下的标注图（format="jpeg"）；upload 模式为空
   ```
   这是**有意的接口版本升级**：action 的消费方（bridge、api_node、测试）都在仓库内，一起重新编译。`capture_task_interfaces` 需要增加对 `sensor_msgs` 的依赖。
   infer 模式下的最终 status：`analyzed`（网关返回 ok/uncertain）、`retake`、`failed`、`cancelled`、`rejected`。
2. **新增 `srv/RunInspection.srv`**：
   ```
   string task_id
   string announce
   float64 prepare_sec
   float64 timeout_sec
   ---
   bool success                 # 仅 status == analyzed 时为 true
   string status                # analyzed|retake|failed|cancelled|rejected|busy|unavailable|invalid|timeout
   string detail
   string task_id
   string capture_id
   string result_json
   sensor_msgs/CompressedImage annotated_image
   ```
   请求字段的语义与 `RunCapture` 完全相同。
3. **`api_node` 新增参数 `pipeline_mode`**，必须与执行器一致，由 launch 统一传入：
   - `upload` 时只注册现有的 `/capture/<task>` 与 `/capture/cancel`；
   - `infer` 时只注册 `/inspect/<task>` 与 `/inspect/cancel`（取消语义同 `/capture/cancel`）。

   避免出现"调用 `/capture/pcb` 却拿到推理结果"这种语义混乱。
4. `/capture_task/state` 增加 `pipeline_mode` 字段（只加不改）。

### 3.3 云端（指令方）协议增量（HTTP v0 只加不改）

infer 模式下，bridge 在任务结束时依次执行：

1. 照常发送最终 event。`result` 字段除原有内容外，增加 `analysis`（即 `result_json` 对应的对象，不含图片 base64）。
2. 新增 `POST /v1/tasks/{task_id}/result-image`：请求体为标注 JPEG 原始字节，请求头带 `X-Capture-Id`、`X-Image-Sha256`、`X-Image-Kind: annotated`。云端返回 `{"status":"received","task_id","capture_id","sha256"}`。可选配置 `return_original_image`，默认 **false**（隐私考虑）。为 true 时再以 `X-Image-Kind: original` 发送原图。
3. infer 模式下**不再调用** `POST /v1/tasks/{task_id}/images`。upload 模式的行为不变。

mock 需要：

- 实现上述新接口，按 task_id 保存结果 JSON 和图片；
- CLI 增加 `mock_capture_cloud.py result <task_id>`，打印结果并给出图片保存路径；
- 继续支持 `--reject-unknown-task`。

### 4.3 舌象服务（关键：PyTorch 版本偏差）

原包锁定 `torch==2.4.0 / torchvision==0.19.0 + cu121`，这个版本**没有 sm_120 内核**，在 5060 上会报 `no kernel image`。处理方式：

1. **GPU 运行环境（偏离原包要求，需记录）**：
   ```bash
   cd /root/roscar-models/tongue_cloud_server_20261015
   python3.12 -m venv .venv && . .venv/bin/activate
   pip install -U pip && pip install -r requirements_core.txt
   pip install torch==2.8.0 torchvision==0.23.0 --index-url https://download.pytorch.org/whl/cu128   # 与 4.2 同版本
   bash scripts/self_check.sh
   python tools/validate_runtime.py --device cuda --out output/gpu_validation.json
   ```
   不修改包内代码、配置、阈值，也不重建 manifest。digest 由代码、模型和配置计算，与 torch 版本无关，运行时只记录版本、不校验。
2. **数值一致性对比（必须做）**：另建 `.venv-cpu-ref`，严格按原包安装 `torch==2.4.0 torchvision==0.19.0`（CPU 版即可），用 `server.py --device cpu` 或 `pipeline_manifest.py run --device cpu`，与 GPU 环境对**同一批图片**推理。图片包括 `examples/synthetic_rgb.png`，再加至少 1 张用户提供的真实舌象照片（照片不入库）。
   通过标准：8 个标签逐项 |Δscore| ≤ 1e-3，所有 decision 一致，status 一致。不通过就停下来报告，**不要**擅自改阈值。结果写进验收文档。
3. 启动（只监听本机，由网关代理）：
   ```bash
   TONGUE_BIND_HOST=127.0.0.1 TONGUE_PORT=8096 bash scripts/start_server.sh passthrough
   ```
4. **显存**：Windows 已占约 2 GB。舌象 11 个模型加上两个 YOLO，预计要占 4–5 GB，两个 CUDA 进程的上下文还要再加约 0.5–1 GB，余量很紧。启动全部服务后，记录 `nvidia-smi` 的显存占用。如果出现 OOM，按以下顺序降级：
   - YOLO 使用 `half=True`；
   - 舌象改为 `--device cpu`，并在文档中写明延迟；
   - 都不行就报告用户。

   同时注意 `.wslconfig` 限制了 WSL 内存为 8 GB，需要观察内存占用。

### 4.4 推理网关（新代码，放进仓库）

位置：`services/inference_gateway/`。这是普通 Python，不是 ROS 包，colcon 不会扫描到。

```

  gateway.py            # ThreadingHTTPServer + 单 GPU worker 队列（上限可配，默认 4）；路由、鉴权、大小限制、超时
  backends/base.py      # Backend 接口：ready() / info() / infer(jpeg, meta) -> dict
  backends/yolo.py      # PCB 与 helmet 共用；延迟 import ultralytics；启动时预热
  backends/tongue.py    # http.client 代理到 127.0.0.1:8096，校验 pipeline/digest/标签集合
  annotate.py           # cv2 画框/类别/分数，tongue 画 roi 与状态；仅用 ASCII 文字
  config.example.yaml   # 模型路径、阈值、device、端口、token 文件路径；真实 config 不入库
  requirements.txt
  start_gateway.sh      # 读取 config，前台运行
  tests/                # 纯 Python，用假后端；不 import torch/ultralytics
  README.md
```

要求：

- 阈值使用模型自带的默认值：PCB 0.20，helmet 0.45 / iou 0.45，imgsz 均为 640，全部写在 config 中可调。网关**不能**擅自改变舌象的阈值。
- 启动时加载并预热所有可用后端。任何一个后端失败时，该任务返回 `model_unavailable`，其他任务照常服务；`/health/ready` 中逐项列出各后端状态。
- 鉴权：config 中的 `token_file` 必须是 0600 权限。车端用 `inference_token_file` 读取同一个 token。
- 监听 `0.0.0.0:8200`。只在内网或隧道中使用，**不要**暴露到公网。
- 在 `scripts/ci_unit_tests.sh` 中加入网关测试，确保 CI 不需要 torch。

### 4.5 让车端（或开发机）能访问网关

依次尝试下列方式，用哪一种都要写进文档：

1. **同网段直连 + Windows 防火墙放行**（推荐长期使用）。需要用户在管理员 PowerShell 中执行，agent 不能代做：
   ```powershell
   New-NetFirewallRule -DisplayName "ROSCAR inference 8200" -Direction Inbound -Protocol TCP -LocalPort 8200 -Action Allow -Profile Private
   # WSL mirrored 模式还受 Hyper-V 防火墙约束：
   New-NetFirewallHyperVRule -Name ROSCAR-Infer-8200 -DisplayName "ROSCAR inference 8200" -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -Protocol TCP -LocalPorts 8200
   ```
   具体命令以微软 WSL 文档为准。放行后，在对端执行 `curl --noproxy '*' http://<5060地址>:8200/health/ready` 验证。
2. **网线直连**：小车 `192.168.100.2` → 5060 `192.168.100.3:8200`。同样需要防火墙放行。
3. **沿用上一轮验证过的受限 SSH 反向隧道**：由 WSL 发起，把小车的 `127.0.0.1:8200` 转发到 WSL 的 `127.0.0.1:8200`，使用一次性密钥，仅允许端口转发、禁止 shell，测试结束后删除密钥。做法见 `docs/2026-10-15WSL模拟云端拍照联调.md`。

本地开发机（`10.0.0.171`）与 5060（`10.0.0.114`）在同一网段，同样适用第 1 种方式。

## 8. 风险与需要用户确认的事项

1. **第三方 helmet 权重的安全性**：`.pt` 是 pickle 格式，加载时会执行其中的代码。该权重来自第三方仓库，仓库 README 和权重型号还对不上。请用户确认来源可信；只在 WSL 隔离目录中加载，不要放到小车上。
2. **舌象使用的 torch 版本与交付包不同**：一致性通过后才可使用，并在文档中注明。如果不通过，就只能用 CPU 运行（延迟要另测），或者换一台非 Blackwell 的 GPU。
3. **8 GB 显存与 8 GB WSL 内存都很紧**：同时加载三个模型可能 OOM，降级顺序见 §4.3。
4. **模型精度未在本车相机上验证**：PCB 在 PKU 数据集上选的阈值、helmet 在 CCTV 场景下的指标、舌象的 OOF 阈值，都**不代表**在本车 640×480 Gemini 画面上的准确率。本轮只验证链路是否打通。PCB 的 README 特别说明，640×480 拍整块板时只能检出毫米级的缺陷。
5. **网络**：Windows 防火墙规则需要用户以管理员身份添加；做不了就用 SSH 隧道。5060 的地址经常变化，每次执行前都要重新确认。
6. **隐私**：面部和舌象图片会经局域网 HTTP 传到 5060。默认不落盘、不回传原图；如果走公网，必须加 TLS，这不在本轮范围内。
7. **face 模型缺失**：需要用户提供。补上后在网关增加一个后端即可，车端不用改。
8. **许可**：YOLO26（PCB）是 AGPL-3.0，PKU 数据集许可不明，只能用于研究和学习。
